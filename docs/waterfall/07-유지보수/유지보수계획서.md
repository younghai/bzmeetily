## 1. 문서 개요

### 1.1 목적

후속 변경·회귀·결함 기록의 지속 절차를 정한다.

### 1.2 적용 범위와 독자

요구사항, 코드, 테스트, 릴리스 상태와 사용자 데이터의 일관성을 다룬다. 제품 기획·개발·QA·릴리스 검토자가 사용한다.

### 1.3 기준과 판정

이 문서는 2026-09-25의 소스와 기록을 바탕으로 한 **검토 초안**이다. 문서화·코드 구현·실행 검증·일반 배포 승인은 서로 다른 상태다.

## 2. 유지보수 유형

| 유형 | 예시 | 확인 방식 |
|------|------|-----------|

| 개선 | 어조·고유명사 정확도 | 원음 대조 전후 비교 |

## 3. 변경 요청 절차

요구사항 변경은 [SRS](../01-요구사항분석/요구사항명세서-SRS.md)의 ID를 수정하고 [RTM](../01-요구사항분석/요구사항추적매트릭스-RTM.md)의 설계·소스·테스트 연결을 갱신한다. 오디오·번역 경로는 원음/기대 텍스트가 있는 재현 사례를 만들고 회귀 검사한다. 개인정보가 포함된 실제 회의 자료는 Git에 추가하지 않는다.

요청에는 영향 사용자, 요구사항 ID, 재현 단계와 검증 결과를 연결한다. 새 기능이나 정책은 문서만 바꾸고 완료했다고 표시하지 않는다.

---

## 4. 서비스 수준과 대응 기준

현재 제품에 승인된 SLA·장애 대응 시간 약속은 없다. 중요한 회의에서 음성 누락/데이터 손실 가능성이 있으면 릴리스 차단으로 우선 분류하고, 원본 오디오·DB 보존을 먼저 수행한다. 시간 약속은 운영 책임자와 사용자 정책이 합의된 후 명시한다.

---

## 5. 정기 점검과 기술 부채

각 후보에서 모델 버전, macOS 권한 변화, Whisper/Ollama 응답, 브라우저별 캡처, 포트 충돌, 처리 지연, RSS/메모리 압력, timeline 누적을 점검한다. 새 버전 검증 결과는 [테스트 결과](../05-테스트/테스트결과보고서.md)에 후보·환경·날짜와 함께 기록한다. 통과했던 오래된 후보의 결과를 새 바이너리에 자동 승계하지 않는다.

우선 기술 부채는 무음 환각 재현, 혼합 입력 정확도, 장시간 자원 측정, 브라우저 E2E, 서명·공증·clean-Mac이다. 각 항목을 [로드맵](../08-검토/우선순위-로드맵.md)과 결함 기록에 연결한다.

---

## 6. 결함 처리와 회귀

1. 사용자 영향과 데이터 손실 가능성을 확인한다. 진행 중 회의의 원본 오디오와 DB를 먼저 보존한다.
2. 기기·OS·모델·입력원·재현 절차·기대/실제 결과를 기록하고 개인정보는 익명화한다.
3. 소스 재현과 실제 앱/localhost 회귀를 분리해 수행한다. 수정 후 같은 시나리오를 다시 실행한다.
4. 릴리스 차단 결함은 [게이트](../06-배포/배포계획서.md)에 반영한다. 운영 중 장애는 [런북](../09-운영런북/장애대응-런북.md)을 따른다.

정식 SLA, 자동 업데이트, 원격 텔레메트리, 사용자 데이터 보존 기간은 현재 승인된 운영 약속이 없다. 향후 제품 정책 결정과 사용자 고지 후 문서화한다.

수정 후 관련 소스 검사뿐 아니라 실제 앱 또는 localhost의 변경 흐름을 실행한다. 과거 후보의 합격을 새 후보에 자동 승계하지 않는다.
