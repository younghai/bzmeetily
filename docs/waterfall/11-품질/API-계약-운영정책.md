# 로컬 API 계약·품질 운영 정책

## 단일 기준과 변경 규칙

실제 라우트는 [app.ts](../../../v2.0/meetily/frontend/local-server/app.ts), 요청·응답 형식은 [contracts.ts](../../../v2.0/meetily/frontend/src/local/contracts.ts) 및 로컬 테스트가 기준이다. [API 설계서](../02-시스템설계/API설계서.md)는 이를 설명하는 문서이며 별도의 배포 API 약속이 아니다.

새 필드·엔드포인트·오류 상태를 바꾸면 다음 순서로 갱신한다: 계약 스키마 → 서버/클라이언트 → 정상·오류 로컬 테스트 → 실제 localhost 요청 → API 설계·RTM·릴리스 기록. 회의 청크 sequence의 멱등성과 번역의 `ja→ko`, 최대 2턴 문맥 제약을 회귀 항목으로 유지한다. 실패 응답을 무조건 성공처럼 표시하지 않는다.

## 보안·가용성

- 서버의 `127.0.0.1` 바인딩과 origin/client 헤더 검사를 유지하고, 외부 네트워크 노출을 출시 전 재확인한다.
- 오디오 업로드 크기, 처리 시간, import 형식과 정적 파일 경로 검사를 유지한다. 원본 오디오·전사·요약을 CI 로그나 공개 샘플에 넣지 않는다.
- DB 준비 지연(503), 빈 전사(409), 권한·모델 실패를 구분해 UI/테스트에 드러낸다.
- 하드웨어 E2E와 장시간 정확도는 API 테스트만으로 대체하지 않는다.

API 계약과 릴리스 후보의 검증 결과가 다르면 실제 코드·테스트·후보 증거를 우선하고 문서를 수정한다. OpenAPI/Postman 파일은 이 저장소에 현재 별도 계약으로 제공되지 않으므로 존재한다고 표기하지 않는다.
